# 回顾 · 2026-09-22 —— 当 AI 产出速率超过人的理解速率

**触发**: 单日 4 个仓库 46 次提交（我 33 次）之后的失控感。
**范围**: 跨仓（`multi-agent-workflow` / `service-intelligence-platform-ui` /
`aiops-apm-anomaly-detector` / `aiops-mcp-servers`）+ 人机协作方式本身。
**本文档放在 backend 仓**，因为它是主仓；跨仓的部分已逐条标注。

---

## 0. 一句话诊断

> **瓶颈不在"AI 写不出代码"，而在"人理解代码的速度"追不上"AI 产出代码的速度"。**
>
> 下面 5 条根因里，有 3 条是这一个根因的不同侧面。

**必须摆在前面的推论**：AI 越强，这个瓶颈越紧 —— 所以它**不会自愈**，只会更严重。

### 1.1 最有价值的一手材料：执行者自述 ≠ 事实

同一天里，同一个执行者（AI）三次把**"我跑了一条命令"**当成了**"我验证了这件事"**：

| 自述 | 事实 |
|---|---|
| "`make doctor` 已修好" | 它**从来没跑通过** —— 目标里用了未定义的 `$(PY)`，实际是绕过 `make` 手跑的 |
| "变异验证通过" | **变异根本没植入**（脚本用了 `./venv`，而那个仓是 `.venv`）—— 测试"红了"另有原因 |
| "四个容器端口全不通" | `nc -z -G 3` **误报**；`nc -v` 逐个测**全通** |

**为什么这三条最有价值**：它们暴露的是**机制**（自述没有产物约束），不是个人能力。
任何执行者——人也好 AI 也好——在"产出快、复核慢"的结构下都会犯同一类错。

## 2. 根因（5 条）

### A. 反馈环带宽不匹配：产出 ≫ 理解 ≫ 共识

代码产出快 → 人看不懂 → 只能依赖"测试绿了 / AI 说验证了"；文档产出也快（134 changelog、
4 份 design）→ 没人读得完 → **共识形成不了**。

对应现象：① 细节与架构脱离掌控；④ 各说各话、架构腐坏；⑬ 文档越多反而越没人读。

### B. 真相没有单一来源，且没有同步机制

| 东西 | 有几份真源 |
|---|---|
| workflow | **数据库**一份 + 仓库 `seed/*.yaml` 一份（seed 对已开通租户**无效且无提示**） |
| agent prompt | DB `agent_configs` 一份 + `seed/agents/*.yaml` 一份 |
| 设计基线 | **4 份 design 文档并存**，没有"哪份有效"的标记 |
| 前端 | Vue `src/` 与 legacy `js/app.js` 双世界并存 |

后果：任何一处改动都可能在别处**静默失效** —— 这就是本仓"静默失败族"的来源。

### C. "完成"没有可核验的定义：自述代替证据

**"看着完成了、其实没接线"的东西有一长串，而它们全都有测试覆盖、测试全绿**：
`ToolPolicy` 零运行期消费方、`--dsn` 分支在装配前 `return`、`severity-medium` 没有 CSS 规则、
`on_reject` 曾是死配置。

所以"AI 选择性偷懒只做 demo"**根因不在 AI** ——
**在于没有人定义过"完成"必须交出什么。**

### D. 并行协作者之间没有工作边界

同一天：同事推 3 次 → 我 rebase 3 次；**changelog 编号撞车 3 处而 git 全程静默**
（文件名不同就不报冲突）。

**最贵的不是冲突，是前提作废**：我基于"APM 用 `POST /tickets` 建单"出了两个方案选项，
等对方选完之后才发现同事的 `ed45670` 早已把建单搬进了 run 内部 ——
**我的问题本身是过时的，而没有任何机制告诉我世界变了。**

### E. 所有约束都落在**最弱的一档**

```
Claude Code hooks : 0
git pre-commit    : 0
CI                : 0
```

| 强度 | 手段 | 违反时会发生什么 | 本项目的现状 |
|---|---|---|---|
| 最强 | **测试** | 本地/CI 变红 | 有测试，但**架构约束一条都没写成测试** |
| 强 | **hooks** | **工具调用被当场拦下** | ❌ 零 |
| 中 | CI 门 | 合并被挡 | ❌ 零 |
| 弱 | 文档约定 | 靠人记得 | ✅ **全部靠这个**（CLAUDE.md 549 行） |
| 无 | 口头约定 | 什么都不会发生 | — |

**这是"不可控"的机制性原因**：不是人不用心，是约束放错了档位。

## 4. 应对措施

### 4.0 总原则：**把约束从"文档"搬到"检查"**

> 一条约束如果**能被机器检查**，就不该只写在文档里。
> 文档只承载**机器查不了**的那部分（判据、取舍、代价）。

这条同时治 A / C / E：检查不需要被记住，也不需要被阅读。

### 4.1 按强度分层（P0 = 最高优先）

| 级别 | 动作 | 治 | 成本 | 验收判据 |
|---|---|---|---|---|
| **P0** | **Claude Code hooks 三条**：<br>① 提交前查 changelog 重号 → 拒<br>② push 前 `git fetch`，落后则拦<br>③ 改动面超阈值出声 | D / E / 10 | 半天 | 连续 10 次提交：0 次 push 被拒、0 次编号撞车 |
| **P0** | **`import-linter` 分层契约**（本仓 §11 已写明"**应当写成测试，比约定可靠**"，但一条未写） | B / E / 4 | 半小时 | 故意加一条 `executor → api` 的 import，`make lint` 必须红 |
| **P1** | **"完成"的定义：证据门** —— 提交信息固定段写「命令 + 退出码 + 关键输出」；<br>**变异验证必须附"变异真的生效"的证据**（`grep -c` 归零 / diff），不是"测试红了" | C / 8 | 纪律 + 半天 | 随机抽 3 条历史提交，只凭提交信息能否复现验证？ |
| **P1** | **`CLAUDE.md` 分层**：正文精简到约 150 行（命令/收尾/Git 约定/约束索引），<br>全文拆到 `docs/constraints/*.md` 按需读 | A / token | 2 小时 | 每个 session 少加载约 500 行 |
| **P1** | **测试基线机器化**：`{"passed": N, "failed": 0}` 落成文件，`make test` 自动对比 | C / 12 | 1 小时 | 基线变化时**自动**报差异，不靠人记 |
| **P2** | **消灭"哪份有效"**：只保留一份当前基线，其余移 `docs/archive/` 并在头部标 Superseded | B / 2 | 2 小时 | 新同事不问人能否指出当前基线是哪份？ |
| **P2** | **`make impact BASE=<sha>`**：输出动了哪些模块 / 跨了几个仓 / 哪些下游消费它 | A / 1 | 1 天 | "本次架构变了什么"能一行答出 |
| **P2** | **ADR（轻量）**：每当一次改动**推翻了原有假设**就加一条 | A / 2 | 半天 | — |
| **P2** | **三级测试漏斗** `test-one` / `test-file` / `test`（全量只在收尾跑一次） | token | 1 小时 | 单次改动全量测试次数 ≤ 1 |

### 4.2 硬规矩（不设工具，靠约定但**可 grep**）

1. **「第三次就抽成命令」** —— 同一串操作第三次出现时，必须先抽成脚本再继续。
   *来源*：本次推 workflow 到租户手搓了 **3 次**才写成 `make sync-workflows`。
2. **「爆炸半径」** —— 一个提交 ≤ 1 个主题。（本次 backend 一天 20 条提交跨 5 个主题，
   意味着人**没有任何自然的停顿点**可以接住。）
3. **「同类问题第二次出现，必须扫全仓」** —— 见 §3 第 3 条。

### 4.3 经验共享机制（跨人 + 跨 session）

**问题**：经验全部沉在**个人的机器**上。本仓的通道是 `CLAUDE.md`（每个 session 自动加载），
但没有任何机制把经验**送进去**。

**机制：不要靠"记录"，要靠"回收"。**

为什么"每人写完记到共享文档"必然失败 —— **134 个 changelog 就是证据**：
它要求人在**当场**多出一份自觉和产能，长期一定烂尾，而且产出量本身会淹没读者。

回收利用的是**已经被强制产生的副产品**：

```
commit message 的「为什么」  ← CLAUDE.md 已强制
changelog                    ← 前端已强制
TODO 新增项                  ← 已经在写
```

```bash
make retro-harvest SINCE="2 weeks ago"
#  1. 扫这段时间的 commit / changelog / TODO 新增
#  2. 用 subagent 提炼候选并三分类（只让结论进主上下文）
#  3. 出三张表：→ 变成检查 / → 进文档 / → 丢弃
#  4. 人只做「点头」（15 分钟），不做回忆与撰写
```

**经验的三个去向**（判据见下）：

| 类型 | 判据 | 去向 |
|---|---|---|
| 可机器查 | 能写成"如果…就红" | **变成检查**（hook / test / lint） |
| 不可机器查、但普适 | 有判据、换台机器还成立 | **进 `docs/lessons/*.md`** |
| 一次性 / 机器相关 / 含凭证 | — | **留本机** |

**一条 lesson 的模板**：

```markdown
## <现象，一句话>
**判据**：<遇到 X 就做 Y —— 要能被 grep、能被判断>
**代价**：<不这么做会出现什么症状 —— 要具体>
**已机器化**：<指向 hook / test；没有就写"无">
```

⭐ **验收规则：没有「代价」的条目不收。**
「`join` 默认 `any`」记不住；「`rca` 因此**从来没拿到过**五维取证摘要」才记得住。

**反向路径**：`docs/lessons/` 的全文按需读，`CLAUDE.md` 只放**一行一条的索引** ——
这样队友的 Claude Code **不用他知道**，开局就带着团队的教训。

### 4.4 团队动作（需要人来定）

| 动作 | 频率 | 谁 |
|---|---|---|
| 过一遍回收出来的三张表 | 每周 15 分钟 | 待定 |
| 一份完整的回顾 | 每个里程碑结束 | 待定 |

## 5. 怎么知道真的改好了（三条总验收）

1. **新同事只读仓库**（不读任何人的本机 memory），**能不能避开已知的坑**？
2. **一条经验如果在仓库里出现两次，说明它没被机器化** —— 该升级成检查。
3. **能否在 5 分钟内从提交列表重建"系统现在长什么样"**？

## 7. 追加：文档受众 / 依赖基线 / TODO 上板

> 本节是回顾当天追加的三点。它们都指向同一件事：**"写出来了"不等于"被用上了"** ——
> 与前 6 节（约束要放进检查、经验要靠回收）是同一条判据的不同侧面。

### 7.1 文档的受众：谁在**什么时刻**读它？

**现状：本仓从未定义过任何一份文档的受众。**
最直接的证据是前端 `CLAUDE.md` 的 changelog 规则 —— 它只说了「**必须生成**」，
**没有说给谁看**。结果是：

| 谁 | 会不会读到那 134 个 changelog |
|---|---|
| 人 | ❌ 134 个散文件，没有索引、没有入口 |
| **LLM** | ❌ **不会自动加载**；它甚至不知道这些文件存在 |

**"写出来了"与"被读到了"之间没有桥。** 这与第 3 节那 134 个文件的存在本身，
是同一件事的两面：产出很容易，被消费很难。

**按受众分类，形态要求完全不同：**

| 受众 | 什么时候读 | 形态要求 | 本仓现状 |
|---|---|---|---|
| **人 · 做决策** | 排期、评审 | 结论先行、**一图胜千言**、删掉过程 | ❌ 1961 行散文 TODO |
| **人 · 执行** | 遇到具体问题时 | 索引 + 精炼正文 | ⚠️ `CLAUDE.md` 549 行约束，**无索引** |
| **LLM · 常驻** | **每个 session** | 判据式、可 grep、**必须短** | ✅ 已有 |
| **LLM · 按需** | 命中特定场景 | **字段化 + 触发路径** | ❌ 散文 + **无触发路径** |
| 谁都不读 | — | **别写** | ← 134 个 changelog 的实际处境 |

**⭐ 给 LLM 看的文档有三条铁律**（与给人看的不一样）：

1. **常驻的必须短** —— 它**每个 session 都吃 token**（`CLAUDE.md` 667 行，其中 549 行是约束）。
2. **按需的必须有触发路径** —— 要在 `CLAUDE.md` 里写「**遇到 X 读 Y**」。
   否则 LLM 永远不知道它存在，**文件等于没写**。
3. **字段化 > 散文** —— `判据 / 代价 / 已机器化` 这类字段能被 grep、能被引用、能被检查；
   一段散文不能。

| Action | 内容 | 验收判据 |
|---|---|---|
| **D1** | 给全仓文档补一张**受众表**（落在 `docs/README.md`），并定成写文档前的第一问：**"谁在什么时刻会读它？"** | 答不出来的文档，**不要写** |
| **D2** | **changelog 改革**：本仓提交信息**已强制写"为什么"**，changelog 与它高度重复 → 二选一：<br>(a) 并入提交信息；(b) 改成 `changelogs/INDEX.md`（一行一条：日期/主题/一句结论/判据）+ 正文**按主题**而非按时间归档 | **任意一个 changelog 文件，能否说出"谁会在什么时候打开它"？** |
| **D3** | 给人看的文档**结论先行 + 一图胜千言**：本节 retro 的根因/应对应有一张图；<br>本仓架构图应从 import 图**自动生成**（**手写的必然过期**） | 人能否在 1 分钟内看懂"系统现在长什么样" |

### 7.2 依赖与工具的团队基线

**现状（本次实测）：**

| 项 | 现状 | 风险 |
|---|---|---|
| Python 依赖 | **无 lock 文件**；只有 `agentscope==2.0.3` 与 `mcp>=1.13,<2.0` 钉了，**其余全是 `>=` 无上界** | 同一份 `pyproject.toml`，在两个人机器上装出**不同的实际版本** |
| Python 版本 | **无 `.python-version`**（3.12 只写在 Dockerfile 和文档里） | — |
| Node 版本 | 有 `package-lock.json` ✅，但**无 `.nvmrc`**、**无 `engines`** | — |
| 容器基镜像 | `FROM python:3.12-slim` —— **两处都未按 digest 钉** | 不同时期构建出**不同的基础镜像** → "在我机器上是好的" |

**⭐ 为什么这条必须落在 `make doctor` 而不是文档里**：
本仓已经有一条成型的判据 ——

> 「机器相关的外部件，**缺了不报错**，只在某条 run 跑到某一步时表现为**结果不对**。」

**版本差异完全属于这一类**：它不会报错，只会在某天表现为"我这跑得通你跑不通"。
`make doctor` 已经是"换机器先跑这个"的入口，把它从"查服务通不通"扩到"**查版本对不对**"，
才是同一套判据下的自然延伸。

| Action | 内容 | 验收判据 |
|---|---|---|
| **E1** | Python 上 `uv` / pip-tools，产出并提交 **lock 文件** | 任意机器上装出**逐包逐版本相同**的环境 |
| **E2** | 版本声明：`.python-version` + 前端 `.nvmrc` + `package.json` 的 `engines` | — |
| **E3** | 容器基镜像**按 digest 钉**（`FROM python:3.12-slim@sha256:…`） | 不同时期重建出**同一个**基座 |
| **E4** | `make doctor` 扩出**版本比对**：`python / node / podman / gh / uv` 的期望 vs 实际 | **新机器上 `make doctor` 全绿 ⇒ 环境与团队基线一致** |

### 7.3 TODO 上板：让人和 LLM 都能**实时感知**

**现状**：`docs/TODO.md` = **33 章节 / 92 条目 / 1961 行**散文；
而 **GitHub Issues 功能是开的、一条没用**（`gh issue list` 返回 `[]`）。

**⭐ 为什么"文档式 TODO"必然失效 —— 它缺四样东西：**

| 缺什么 | 后果 |
|---|---|
| **状态** | 谁在做、做到哪、什么时候该有结论 —— 全没有 |
| **视图** | "P0 在 1961 行的哪一段？"只能全文搜 |
| **更新触发** | 改完代码没人回来删条目 ⇒ **只会单调增长** |
| **可查询** | LLM 要"实时感知"得把 1961 行**读进上下文** |

**看板补的正是这四样，而成本近乎为零** —— `gh` **已经是本仓的既有依赖**
（PR 闭环靠它；缺 gh 会让工单闭环彻底没回音）：

```bash
gh issue list --label P0 --json number,title,labels     # LLM 一条命令拿到全部 P0
gh issue create --label debt --title "…" --body "…"     # 回收机制的落点
```

| Action | 内容 | 验收判据 |
|---|---|---|
| **T1** | TODO 条目迁成 **GitHub Issues**（label：严重度 / 领域 / 根因族）+ Projects 看板；<br>`TODO.md` 只留**一行索引**与"不是待办"的部分（已完成留痕、方法论） | 问"还有哪些 P0"——**一条命令答得出来** |
| **T2** | **消灭机制**：每条债只有三个去向，**必须选一个**：<br>① **机器化**（变成测试/hook ⇒ 它**消失**了）② **上板**（有 owner 有状态）③ **关闭**（决定不做） | ⭐ **留在文档里的债 = 没人管的债** |
| **T3** | 给人看的看板要"**一眼**"：列 = 严重度 × 状态。<br>**不要把 1961 行塞进一个表格** —— 那是把文档搬了个地方，不叫可视化 | 扫一眼能否答出"现在最该做哪三件" |

**⭐ 为什么 T1 对 LLM 尤其重要（也是 token 效率的核心差别）**：

- **看板 = 结构化 + 可查询** ⇒ LLM **一条命令**拿到答案（几十 token）
- **文档 = 非结构化 + 要读全** ⇒ LLM **必须把全文读进上下文**（几万 token）

**同一个问题，两条路的代价差两个数量级。** 这与 §4.3「经验共享」是同一条判据 ——
**让知识活在被查询的地方，而不是被阅读的地方。**

### 7.4 三点追加的优先级

| 级别 | Action | 治 | 成本 |
|---|---|---|---|
| **P0** | **E4** `make doctor` 扩版本比对（它拦得住 E1–E3 的所有缺口） | 环境差异 | 半天 |
| **P0** | **T1/T2** TODO 上板 + 消灭机制 | 人与 LLM 都感知不到债 | 1 天（迁移）+ 长期习惯 |
| **P1** | **E1/E2/E3** lock 文件 + 版本声明 + 镜像 digest | 环境不可复现 | 半天 |
| **P1** | **D1** 受众表 + 写文档前的第一问 | 文档无人读 | 2 小时 |
| **P2** | **D2** changelog 改革 | 上万行写出即废 | 半天（含决策） |
| **P2** | **D3** 结论先行 + 架构图自动生成 | 人的理解速度 | 1 天 |

## 8. 两个必须说出口的提醒

1. **工具治不了"自述 ≠ 事实"。** hooks 能拦"**没跑**检查"，拦不住"**跑了但结论错**"
   （§1.1 的三次实例全属后者）。那一半只能靠"产物而非自述"的纪律 + 人抽查。
2. **更多文档 ≠ 更多控制。** 134 个 changelog + 4 份 design + 1961 行 TODO 已经证明：
   它们消耗的是**每个人的阅读带宽**，而带宽**就是**控制力。
   **token 效率的真正含义是：花在"检查"上的每一分都值，花在"叙述"上的大部分不值。**
