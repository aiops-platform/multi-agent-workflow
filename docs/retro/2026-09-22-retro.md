# 回顾 · 2026-09-22 —— 当 AI 产出速率超过人的理解速率

**触发**: 单日 4 个仓库 46 次提交（我 33 次）之后的失控感。
**范围**: 跨仓（`multi-agent-workflow` / `service-intelligence-platform-ui` /
`aiops-apm-anomaly-detector` / `aiops-mcp-servers`）+ 人机协作方式本身。
**本文档放在 backend 仓**，因为它是主仓；跨仓的部分已逐条标注。

---

## 0. 一句话诊断

> **瓶颈不在"AI 写不出代码"，而在"人理解代码的速度"追不上"AI 产出代码的速度"。**
>
> 下面 5 条根因里，有 3 条是这一个根因的不同侧面。

**必须摆在前面的推论**：AI 越强，这个瓶颈越紧 —— 所以它**不会自愈**，只会更严重。

### 1.1 最有价值的一手材料：执行者自述 ≠ 事实

同一天里，同一个执行者（AI）三次把**"我跑了一条命令"**当成了**"我验证了这件事"**：

| 自述 | 事实 |
|---|---|
| "`make doctor` 已修好" | 它**从来没跑通过** —— 目标里用了未定义的 `$(PY)`，实际是绕过 `make` 手跑的 |
| "变异验证通过" | **变异根本没植入**（脚本用了 `./venv`，而那个仓是 `.venv`）—— 测试"红了"另有原因 |
| "四个容器端口全不通" | `nc -z -G 3` **误报**；`nc -v` 逐个测**全通** |

**为什么这三条最有价值**：它们暴露的是**机制**（自述没有产物约束），不是个人能力。
任何执行者——人也好 AI 也好——在"产出快、复核慢"的结构下都会犯同一类错。

## 2. 根因（5 条）

### A. 反馈环带宽不匹配：产出 ≫ 理解 ≫ 共识

代码产出快 → 人看不懂 → 只能依赖"测试绿了 / AI 说验证了"；文档产出也快（134 changelog、
4 份 design）→ 没人读得完 → **共识形成不了**。

对应现象：① 细节与架构脱离掌控；④ 各说各话、架构腐坏；⑬ 文档越多反而越没人读。

### B. 真相没有单一来源，且没有同步机制

| 东西 | 有几份真源 |
|---|---|
| workflow | **数据库**一份 + 仓库 `seed/*.yaml` 一份（seed 对已开通租户**无效且无提示**） |
| agent prompt | DB `agent_configs` 一份 + `seed/agents/*.yaml` 一份 |
| 设计基线 | **4 份 design 文档并存**，没有"哪份有效"的标记 |
| 前端 | Vue `src/` 与 legacy `js/app.js` 双世界并存 |

后果：任何一处改动都可能在别处**静默失效** —— 这就是本仓"静默失败族"的来源。

### C. "完成"没有可核验的定义：自述代替证据

**"看着完成了、其实没接线"的东西有一长串，而它们全都有测试覆盖、测试全绿**：
`ToolPolicy` 零运行期消费方、`--dsn` 分支在装配前 `return`、`severity-medium` 没有 CSS 规则、
`on_reject` 曾是死配置。

所以"AI 选择性偷懒只做 demo"**根因不在 AI** ——
**在于没有人定义过"完成"必须交出什么。**

### D. 并行协作者之间没有工作边界

同一天：同事推 3 次 → 我 rebase 3 次；**changelog 编号撞车 3 处而 git 全程静默**
（文件名不同就不报冲突）。

**最贵的不是冲突，是前提作废**：我基于"APM 用 `POST /tickets` 建单"出了两个方案选项，
等对方选完之后才发现同事的 `ed45670` 早已把建单搬进了 run 内部 ——
**我的问题本身是过时的，而没有任何机制告诉我世界变了。**

### E. 所有约束都落在**最弱的一档**

```
Claude Code hooks : 0
git pre-commit    : 0
CI                : 0
```

| 强度 | 手段 | 违反时会发生什么 | 本项目的现状 |
|---|---|---|---|
| 最强 | **测试** | 本地/CI 变红 | 有测试，但**架构约束一条都没写成测试** |
| 强 | **hooks** | **工具调用被当场拦下** | ❌ 零 |
| 中 | CI 门 | 合并被挡 | ❌ 零 |
| 弱 | 文档约定 | 靠人记得 | ✅ **全部靠这个**（CLAUDE.md 549 行） |
| 无 | 口头约定 | 什么都不会发生 | — |

**这是"不可控"的机制性原因**：不是人不用心，是约束放错了档位。

## 4. 应对措施

### 4.0 总原则：**把约束从"文档"搬到"检查"**

> 一条约束如果**能被机器检查**，就不该只写在文档里。
> 文档只承载**机器查不了**的那部分（判据、取舍、代价）。

这条同时治 A / C / E：检查不需要被记住，也不需要被阅读。

### 4.1 按强度分层（P0 = 最高优先）

| 级别 | 动作 | 治 | 成本 | 验收判据 |
|---|---|---|---|---|
| **P0** | **Claude Code hooks 三条**：<br>① 提交前查 changelog 重号 → 拒<br>② push 前 `git fetch`，落后则拦<br>③ 改动面超阈值出声 | D / E / 10 | 半天 | 连续 10 次提交：0 次 push 被拒、0 次编号撞车 |
| **P0** | **`import-linter` 分层契约**（本仓 §11 已写明"**应当写成测试，比约定可靠**"，但一条未写） | B / E / 4 | 半小时 | 故意加一条 `executor → api` 的 import，`make lint` 必须红 |
| **P1** | **"完成"的定义：证据门** —— 提交信息固定段写「命令 + 退出码 + 关键输出」；<br>**变异验证必须附"变异真的生效"的证据**（`grep -c` 归零 / diff），不是"测试红了" | C / 8 | 纪律 + 半天 | 随机抽 3 条历史提交，只凭提交信息能否复现验证？ |
| **P1** | **`CLAUDE.md` 分层**：正文精简到约 150 行（命令/收尾/Git 约定/约束索引），<br>全文拆到 `docs/constraints/*.md` 按需读 | A / token | 2 小时 | 每个 session 少加载约 500 行 |
| **P1** | **测试基线机器化**：`{"passed": N, "failed": 0}` 落成文件，`make test` 自动对比 | C / 12 | 1 小时 | 基线变化时**自动**报差异，不靠人记 |
| **P2** | **消灭"哪份有效"**：只保留一份当前基线，其余移 `docs/archive/` 并在头部标 Superseded | B / 2 | 2 小时 | 新同事不问人能否指出当前基线是哪份？ |
| **P2** | **`make impact BASE=<sha>`**：输出动了哪些模块 / 跨了几个仓 / 哪些下游消费它 | A / 1 | 1 天 | "本次架构变了什么"能一行答出 |
| **P2** | **ADR（轻量）**：每当一次改动**推翻了原有假设**就加一条 | A / 2 | 半天 | — |
| **P2** | **三级测试漏斗** `test-one` / `test-file` / `test`（全量只在收尾跑一次） | token | 1 小时 | 单次改动全量测试次数 ≤ 1 |

### 4.2 硬规矩（不设工具，靠约定但**可 grep**）

1. **「第三次就抽成命令」** —— 同一串操作第三次出现时，必须先抽成脚本再继续。
   *来源*：本次推 workflow 到租户手搓了 **3 次**才写成 `make sync-workflows`。
2. **「爆炸半径」** —— 一个提交 ≤ 1 个主题。（本次 backend 一天 20 条提交跨 5 个主题，
   意味着人**没有任何自然的停顿点**可以接住。）
3. **「同类问题第二次出现，必须扫全仓」** —— 见 §3 第 3 条。

### 4.3 经验共享机制（跨人 + 跨 session）

**问题**：经验全部沉在**个人的机器**上。本仓的通道是 `CLAUDE.md`（每个 session 自动加载），
但没有任何机制把经验**送进去**。

**机制：不要靠"记录"，要靠"回收"。**

为什么"每人写完记到共享文档"必然失败 —— **134 个 changelog 就是证据**：
它要求人在**当场**多出一份自觉和产能，长期一定烂尾，而且产出量本身会淹没读者。

回收利用的是**已经被强制产生的副产品**：

```
commit message 的「为什么」  ← CLAUDE.md 已强制
changelog                    ← 前端已强制
TODO 新增项                  ← 已经在写
```

```bash
make retro-harvest SINCE="2 weeks ago"
#  1. 扫这段时间的 commit / changelog / TODO 新增
#  2. 用 subagent 提炼候选并三分类（只让结论进主上下文）
#  3. 出三张表：→ 变成检查 / → 进文档 / → 丢弃
#  4. 人只做「点头」（15 分钟），不做回忆与撰写
```

**经验的三个去向**（判据见下）：

| 类型 | 判据 | 去向 |
|---|---|---|
| 可机器查 | 能写成"如果…就红" | **变成检查**（hook / test / lint） |
| 不可机器查、但普适 | 有判据、换台机器还成立 | **进 `docs/lessons/*.md`** |
| 一次性 / 机器相关 / 含凭证 | — | **留本机** |

**一条 lesson 的模板**：

```markdown
## <现象，一句话>
**判据**：<遇到 X 就做 Y —— 要能被 grep、能被判断>
**代价**：<不这么做会出现什么症状 —— 要具体>
**已机器化**：<指向 hook / test；没有就写"无">
```

⭐ **验收规则：没有「代价」的条目不收。**
「`join` 默认 `any`」记不住；「`rca` 因此**从来没拿到过**五维取证摘要」才记得住。

**反向路径**：`docs/lessons/` 的全文按需读，`CLAUDE.md` 只放**一行一条的索引** ——
这样队友的 Claude Code **不用他知道**，开局就带着团队的教训。

### 4.4 团队动作（需要人来定）

| 动作 | 频率 | 谁 |
|---|---|---|
| 过一遍回收出来的三张表 | 每周 15 分钟 | 待定 |
| 一份完整的回顾 | 每个里程碑结束 | 待定 |

## 5. 怎么知道真的改好了（三条总验收）

1. **新同事只读仓库**（不读任何人的本机 memory），**能不能避开已知的坑**？
2. **一条经验如果在仓库里出现两次，说明它没被机器化** —— 该升级成检查。
3. **能否在 5 分钟内从提交列表重建"系统现在长什么样"**？

## 6. 值得继续保持的（不要在这次整改里丢掉）

| 项 | 为什么值得留 |
|---|---|
| **`CLAUDE.md` 的"判据式约束"** | "谁持有密钥，谁不执行不可信代码" —— **有判据才能被 grep、被引用、被违反时一眼看出** |
| **提交信息写「为什么」** | 本项目最有价值的资产；§4.3 的回收机制**全靠它**才有料可收 |
| **plan mode 的强制回人** | 本次回顾当天它挡住了**两个错误前提**。目前唯一真正生效的"人在回路"机制 |
| **变异验证** | 贵，但当天救场两次。**前提是必须附"变异生效"的证据** |
| **真环境零 LLM 探针** | 不烧 token 就能验真实链路（探针工单 + 按显式 id 清理） |
| **「静默失败」作为一个被命名的类别** | 有名字才能被讨论、被 grep、被写成检查。本次新命名三个变体：两个绿信号互相矛盾 / `when` 恒走同一分支 / 手工单被送去投递口 |

## 7. 两个必须说出口的提醒

1. **工具治不了"自述 ≠ 事实"。** hooks 能拦"**没跑**检查"，拦不住"**跑了但结论错**"
   （§1.1 的三次实例全属后者）。那一半只能靠"产物而非自述"的纪律 + 人抽查。
2. **更多文档 ≠ 更多控制。** 134 个 changelog + 4 份 design + 1961 行 TODO 已经证明：
   它们消耗的是**每个人的阅读带宽**，而带宽**就是**控制力。
   **token 效率的真正含义是：花在"检查"上的每一分都值，花在"叙述"上的大部分不值。**
