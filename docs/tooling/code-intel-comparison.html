结论先行。三种方式不是替代关系，是分工关系。实测判定：

  • codegraph 答对 7/8，成本 0 token / 4.66 秒 —— 应当常态化使用，替代大部分「谁调用谁 / 定义在哪」的检索。
  • understand-anything 答对 6/8，成本 824,147 token / 14 个子代理 / 16.4 分钟 —— 成本差约 200 倍，但它有一样另外两家都没有的东西：架构叙事（分层 + 导览）。只在「给新人做导览」时值得跑一次。
  • grep 永远不可替代：字面常量、状态核查、跑服务探接口只有它能做，且零成本零安装。

⚠️ 本结论的边界写在 §7 局限，请连同结论一起读 —— 尤其是 n=1 与「题目由我出」这两条。

2 · 三种方式是什么

方式原理在本次实测中的形态
grep
基线		 逐次正则匹配 + 读文件。无索引、无状态。 5 次 Bash 调用答完 8 题；输出是原文行。
understand-anything
v2.7.5		 7 阶段流水线：扫描 → 语义分批 → 每个批次派一个 LLM 子代理读文件并产出图节点/边 → 合并 → 验收 → 架构分层 → 生成导览。 14 个子代理、103 文件、产出 304 节点 / 537 边的摘要图 + 10 个架构层 + 14 步导览。
codegraph
v1.6.0		 tree-sitter 解析 AST + SQLite(FTS5) 存储。节点 = 函数/类/变量/import，边 = 调用/导入/继承。MCP 工具与 CLI 同源。 一条命令 4.66 秒建完 1,185 节点 / 2,739 边。explore 附带当次从盘上重读的 verbatim 原文。

一个决定性差异：摘要 vs 原文。understand-anything 把源码交给 LLM 总结；codegraph 把源码原样给你，并在输出里明确声明：

The code below is the verbatim, current on-disk source … re-read from disk on this call
and line-numbered, byte-for-byte identical to what the Read tool returns.
It is NOT a summary, outline, or stale cache.

后面 Q3/Q4 的分差，根源全在这里 —— LLM 摘要天然丢字面常量（URL、配置键、映射表），而原文天然不丢。

4.1 增量更新：codegraph 的三层机制（逐层实测）

「索引会不会过期」是选型时最该问的问题 —— 一份会过期的图比没有图更危险，因为它给出确信的错误答案。codegraph 用了三层来防这件事，逐层验证如下：

层机制实测结论
① 文件监听
自动同步		 由一个后台守护进程（daemon）承担：监听仓库内的 Unix socket <repo>/.codegraph/daemon.sock（每仓一个），用本地 socket "share one background server across sessions" —— 多个 agent 会话共享同一份索引与监听。
监听走原生 OS 事件（macOS FSEvents / Linux inotify / Win ReadDirectoryChangesW），防抖默认 2000 ms（CODEGRAPH_WATCH_DEBOUNCE_MS 可调，钳 [100 ms, 60 s]）。
daemon 只由 codegraph serve --mcp 拉起 —— 实测跑了 init / query / sync / status / files 一串 CLI 后，daemon 仍报 No daemon running，直到起了 serve 才出现。可用 --no-watch 或 CODEGRAPH_NO_DAEMON=1 关闭。		 ✅ 已验证
daemon 起来后，全程未跑 sync：
· 造新符号 → 6 秒后查询即命中；删该文件 → 6 秒后自动移除
· daemon.log 记录 Auto-synced 1 file(s) in 253ms / 2ms
· serve 进程退出后 daemon 继续存活（exit 0 后仍运行 50 秒）
· 停掉 daemon 期间改的文件，重启后自动补齐：日志 Caught up 1 file(s) changed since last run，无需手动 sync
② Pending
横幅		 防抖窗口内，若 MCP 工具响应会引用到尚未同步的文件，响应开头加 ⚠️ 横幅点名该文件、指示 agent 直接 Read。未被引用的待同步文件则以脚注给出。codegraph status 相应显示 ### Pending sync: 段，列出文件与编辑时长。 ⚠️ 未验证
文档有明确描述，但我没能构造出触发所需的时序（需正好卡在 2 秒防抖窗口内查询一个刚改动的文件）。
如实标注为未验证，不计入对比优势。
③ 手动 sync 给 watcher 被禁用的场景（沙箱环境 / --no-watch / CODEGRAPH_NO_DAEMON=1），或脚本不进 agent 会话时做前置同步。带 -q，文档写明 "for git hooks"。 ✅ 已验证

4.2 daemon 的生命周期（「常驻」到底指什么）

问题事实（daemon.log 与实测）
它是什么一个按项目的后台守护进程，监听仓库内的 Unix socket .codegraph/daemon.sock，供多个会话共享
谁拉起它只有 codegraph serve --mcp。纯 CLI 命令不会拉起（已实测）
活多久空闲 300000 ms（5 分钟）自动退出 —— 日志原文：Idle timeout 300000ms
退出后怎么办下次有客户端连上时重新拉起，并自动补齐缺位期间的改动
怎么关CODEGRAPH_NO_DAEMON=1（每个会话各自进程，不共享）

所以准确说法不是「MCP server 必须永远开着」，而是 「需要一个活着的 daemon」：agent 会话期间它在，会话结束 5 分钟后它退。这也是本报告 §6 推荐「常态用 codegraph」时必须一并落实的前提。

一个实测出来的缺口：无 daemon 时，CLI 查询会静默返回过期结果。

复现（daemon 已停、文件已改）：codegraph query <新符号> → No results found —— 文件明明存在。分两种情况：

  • codegraph status 会警告：实测输出 Pending Changes: Added: 1 files 并提示 Run "codegraph sync" to update the index。
  • query / node / callers 不警告，直接读库返回。

README 说明第 ② 层 Pending 横幅是加在 MCP 工具响应上的 —— 那在 MCP 模式（daemon 活着）下应当覆盖此缺口。但纯 CLI 用法没有这层保护：用 CLI 时，若不确定 daemon 是否活着，先跑一次 status。

5 · 优势 / 劣势 / 代价

grep 基线 · 不可替代

维度内容
优势 · 零成本、零安装、零维护 —— 没有任何前置动作
· 永远最新，不存在索引与代码不一致
· 无盲区：字面常量、配置键、注释、非代码文件，什么都能搜
· 可精确到任意粒度：正则、上下文行数、文件类型过滤
劣势 · 只能逐次问，每次都是冷启动
· 跨文件关系要人肉拼接（「谁调用 X」要 grep 名字 + 判断真假阳性 + 追 import）
· 没有影响面分析：改一个函数前想知道波及哪些测试，grep 答不了
· 字面命中 ≠ 真命中（本次实测中我就被注释里的 ticket-done 骗过一次，差点得出错结论）
代价时间与 token 随问题量线性增长。本项目实测：29%–50% 的 Bash 调用花在这上面。

understand-anything 有独特价值 · 但贵 200 倍

维度内容
优势 · 唯一能产出「架构叙事」的一家：10 个架构层（server-entry / mcp-tools / backends / security / core …）+ 14 步导览，每步带中文说明
· 输出是人话摘要，适合新人快速建立心智模型，不需要读源码
· 会做跨批次的关系推断（tested_by、configures、deploys 等语义边），这是纯语法解析做不到的
· 自带校验阶段（本次 0 issues）
劣势 · 字面常量系统性丢失：URL、配置键、映射表在摘要里没了 → Q3 直接答不出、Q4 清单缺失
· 图内可能自相矛盾：Q7 出现「datasource.py 节点自称 10 个只读工具」与其它节点/README 打架，且没有任何机制发现这个矛盾
· 没有 callers/callees/impact 这类查询工具 —— 图建好了但你不能直接问「谁调用 X」
· 索引是快照，代码变了要重跑（增量机制存在但本轮未验证）
代价 824,147 token / 14 个子代理 / 16.4 分钟（该仓规模下）。需要 Node ≥22 + pnpm，首次要构建插件。
注：若只答 8 题而不建图，单次图查询约 76,000 token —— 但那是建立在已付 824k 建图成本之上。

codegraph 性价比最优

维度内容
优势 · 0 token / 4.66 秒建 1,185 节点 —— 确定性解析，不走 LLM
· callers / callees / impact 直接回答「谁调用谁 / 改前影响面」，正好打在 Bash 用量最大的那 29% 上
· explore 给 verbatim 原文（当次从盘重读）→ 字面常量不丢，Q3/Q4 因此完胜
· 增量更新有三层机制（文件监听自动同步 / Pending 横幅 / 手动 sync）：自动同步与手动 sync 均已实测成立，且 daemon 缺位期间的改动会在重启时自动补齐（Caught up N file(s) changed since last run）—— 逐层结论见 §4.1 / §4.2
· MIT 许可、289 MB 自包含二进制、零运行时依赖；索引器自带 .gitignore 防止数据库入库
劣势 · 不给语义摘要：它告诉你「build_query 在 36–78 行、被 5 个地方调用」，不告诉你「这个模块干什么用的」 —— 后者仍需 LLM 或人
· 没有架构分层 / 导览，给不了「这个仓长什么样」的整体叙事
· 同样抓不到嵌套闭包（与 understand-anything 同盲区）
· 每个仓要单独 init，会在仓里留下 3.8 MB 索引目录
· 自动同步依赖一个活着的 daemon（只由 serve --mcp 拉起，空闲 5 分钟自动退）：纯 CLI 用法下不启监听，需手动 sync；且此时 query/callers 会静默返回过期结果，只有 status 提示 Pending Changes（见 §4.2）
· 默认收集匿名遥测（codegraph telemetry off 可关）—— 说明里承诺不含代码/路径/符号名
代价每仓 3.8 MB 索引 + 一次性 289 MB 二进制下载。无 token 成本、无 LLM 成本。命令实测约 1–2 秒/次。

组合用法（推荐落地形态）。不把它们当竞品，当不同粒度：

  1. 常态：仓库 codegraph init 一次，并把 MCP server 注册上（否则自动同步不会启用，见 §4.2）→ 之后「找定义 / 找调用方 / 看影响面 / 取字面常量」全走 codegraph，grep 退到「它查不到的边角」。
    若暂不注册 MCP server、只用 CLI：每次查询前先跑一次 codegraph status —— 它会告诉你有没有 Pending Changes，而 query/callers 不会。
  2. 零散：跑服务、探接口、验状态照旧走 bash + curl。
  3. 里程碑：新人接手或需要对外讲架构时，跑一次 understand-anything 出导览，用完即弃，不进 CICD、不做常规依赖。

7 · 这份结论的局限（请连同结论一起读）

局限影响
n = 1只测了 1 个仓、1 种语言（Python）、1 个规模（12k 行）。更大或混合语言的仓未必是这个结论 —— 官方 benchmark 声称大仓收益更大，我没有验证。
题目由我出8 题取自一次真实会话，但由我选择，可能无意间偏向某方的强项。题目数太少，7/8 与 6/8 的差距不具统计显著性。
判分含主观性Q4、Q7 的判定（「核心对清单缺」算 ✅ 还是 ⚠️）由我裁量。换个人可能给出 6/8 与 6/8。

daemon 的存活边界未穷举codegraph 的「空闲 5 分钟退出、下次连上自动补齐」是我从单次日志读到的。没测：同时开多个项目、多个 agent 会话并发时的行为；daemon 被杀（非 SIGTERM）后索引的一致性；以及 5 分钟超时是否可配。
